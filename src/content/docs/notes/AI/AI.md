## MCP

一种开放协议，用于标准化 AI 应用与外部工具、数据源之间的交互方式。

即，AI 应用连接外部工具和数据的一套统一标准。

假设开发一个 AI Agent，需要访问 MySQL、GitHub、文件系统等外部服务。没有 MCP 时，开发者通常需要分别实现不同服务的接口适配逻辑。引入 MCP 后，Agent 可以通过统一协议发现和调用不同 MCP Server 提供的能力。

MCP 主要包含三个角色：

| 角色       | 作用                                               |
| ---------- | -------------------------------------------------- |
| MCP Host   | AI 应用，例如 Agent 所在的应用程序                 |
| MCP Client | 由 Host 创建，负责与 MCP Server 建立连接、交换消息 |
| MCP Server | 对外提供工具、资源和提示词等能力                   |

MCP 的三类核心能力是：

| 能力      | 作用                   | 示例                           |
| --------- | ---------------------- | ------------------------------ |
| Tools     | 执行操作               | 查询数据库、调用 API、创建文件 |
| Resources | 提供可读取的上下文数据 | 文件内容、数据库结构、文档     |
| Prompts   | 提供可复用的提示词模板 | 代码审查模板、SQL 分析模板     |



## Agent

Agent 的主要组成部分：感知、决策、执行、记忆

- 感知

  负责接收和理解外部信息。比如：图片、文件或 API 返回的结构化数据

- 决策

  Agent 的大脑，即 LLM。它负责分析当前任务，进行意图识别，决定下一步做什么

- 执行

  执行决策，一般是工具调用。比如：调用外部 API、查数据库、跑代码等

- 记忆

  让 Agent 记住历史信息。分为短期记忆和长期记忆：
  1）短期记忆，当前对话上下文，当前任务的执行记录；2）长期记忆，重要信息落库，便于下次使用

## RAG

RAG 的类型



**Embedding 技术早都用于推荐、搜索系统等领域，那么目前的 RAG 底层也是向量匹配，无非是用于 LLM 来增强 context？**

RAG 并没有发明 Embedding 或向量检索。Embedding 和向量匹配早已大量应用于推荐系统、搜索系统等领域。RAG 本质上是把这些成熟的信息检索技术接到 LLM 前面，把检索到的信息作为上下文，从而增强 LLM 的生成能力。

甚至可以进一步说，RAG 真正的新东西并不是“向量数据库”，而是：

```
传统 Information Retrieval
            +
        LLM Generation
```

这也是为什么你之前说：

> “RAG 技术一直演进，但核心还是文档切分、向量化、相似度计算。”

这个判断对经典 Dense RAG 是基本成立的。

不过到了 Agentic RAG / Modular RAG / Graph RAG，核心逐渐从：

```
怎么把文档检索出来
```

变成：

```
什么时候检索
检索什么
去哪个数据源
用什么检索方式
是否需要二次检索
如何判断证据够不够
```

### LangChain

LanguageChain 是一个专门用来开发大语言模型应用的框架，核心就是把 LLM 的能力和外部工具、数据源穿起来。

六大核心组件如下：

1. Models
2. Prompt Templates
3. Memory
4. Chains
5. Agents
6. Tools



### 大模型的返回类型选型

LangChain4j AI Service 的返回类型主要分为四类：

1. 同步单结果：`String`、枚举、布尔值、数字、POJO、集合等；

   - `string`：同步返回完整文本。

     适合：短文本生成、标题生成、Prompt 优化、摘要生成等

     不适合：长篇代码生成、用户需要即时看到生成进度等

   - 枚举、布尔值和数字：分类或判断。

     LangChain4j 可以把模型输出解析成普通 Java 类型。

     适合：意图识别、内容分类、风险判断等

   - POJO、Record：结构化输出

     要求模型直接返回业务对象。

     适合：数据抽取等。

     但要注意需要校验结果，因为模型生成的不一定符合结构。

   - `List<T>、Set<T>` 集合：返回集合

     适合：返回关键词列表、功能点列表等

2. 带元数据结果：`Result<T>`；

   - `Result<T>`：结果内容加模型元数据

     Token 用量、结束原因、工具调用记录等信息

3. 异步单结果：`CompletableFuture<T>`、`CompletionStage<T>`、`Mono<T>`；

   - `CompletableFuture<T>`：异步返回一个结果

     适合：同时调用多个相互独立的模型、后台任务、不需要流式输出，但不想阻塞调用线程等

   - `CompletionStage<T>`：同上

   - `Mono<T>`：Reactor 异步单结果

     适合：项目本身采用 WebFlux、上下游全部使用 Reactor、调用只产生一个最终结果等

4. 流式结果：`TokenStream`、`Flux<String>`、`Flow.Publisher<?>`、`Flux<AiServiceStreamingEvent>`。

总结：

```
只要最终文本                  → String
需要明确业务结构              → enum / POJO / List
需要调用元数据                → Result<T>
需要一个异步最终结果          → CompletableFuture<T> / Mono<T>
只需要流式文本                → Flux<String>
需要监听工具等完整流式过程    → TokenStream
```







**什么时候使用 human-in-the-loop？**

下述以 SyncUp 中的创建/删除队伍为例说明：

| 维度                     | 方案 1：Draft/PendingAction | 方案 2：LangChain4j HITL      |
| ------------------------ | --------------------------- | ----------------------------- |
| 适合场景                 | 单次创建、修改、删除        | 多步骤 Agent 工作流           |
| 系统复杂度               | 较低                        | 较高                          |
| 是否需要保存 Agent 状态  | 不需要                      | 通常需要                      |
| 用户等待期间是否占用线程 | 不需要                      | 取决于实现                    |
| 与业务系统耦合           | 主要在业务层                | 业务层与 Agent 编排层都会涉及 |
| 审计、幂等和权限控制     | 容易实现                    | 仍需额外实现                  |
| 暂停后继续执行后续步骤   | 较弱，但通常不需要          | 强                            |
| 当前 SyncUp 是否需要     | 需要                        | 暂时没有必要                  |

对于“创建一个队伍”来说，确认完成后只需要调用一次 `TeamApplicationService.createTeam()`，后面没有必须由 Agent 继续完成的工作流，因此 HITL 带来的 checkpoint、恢复、AgenticScope 管理价值不大。
