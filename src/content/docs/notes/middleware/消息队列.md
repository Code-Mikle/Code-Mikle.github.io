## 消息队列

消息队列（Message Queue，简称 MQ）是一种实现应用程序间通信的中间件。本质上就是一个异步通信的中间件，在生产者和消费者之间架一个 broker 做缓冲，一个或多个生产者把消息发送到队列里，消费者什么时候有空什么时候来获取并处理这些消息，从而让两个系统不必同步等待彼此完成。

**为什么需要 MQ？**

> 在用户下单场景中，如果不使用消息队列，订单服务可能在完成订单创建和库存扣减后，还要同步调用积分、短信、通知等服务。这样会带来三个主要问题：
>
> - 响应时间长
>
>   订单接口需要等待所有下游服务执行完成才能返回，而积分、短信等其实并不需要阻塞用户的下单流程。引入 MQ 后，可以把这些非核心操作异步执行，降低接口响应时间；
>
> - 系统耦合严重
>
>   如果订单服务直接调用积分、短信等服务，那么每增加一个下游业务（风控、推荐、数据分析），都可能需要修改订单服务，扩展性差。使用 MQ 后，订单服务只需要发布订单创建事件，由不同消费者自行订阅处理，从而实现服务解耦，提高系统扩展性；
>
> - 无法应对突发流量
>
>   高并发场景下，如果请求直接传递给下游服务，而下游处理能力有限，就可能出现请求超时、线程池耗尽、数据库连接池打满等问题。MQ 可以作为缓冲层，将瞬时流量暂存在队列中，由消费者按自身处理能力逐步消费，实现削峰填谷。
>
> 所以消息队列主要解决的就是三个问题：异步、解耦和削峰。

例如用户下单：

```
用户下单
   ↓
订单服务
   ├── 保存订单
   ├── 发消息 → MQ
   ↓
立即返回“下单成功”

MQ
 ├──→ 库存服务：扣库存
 ├──→ 积分服务：增加积分
 ├──→ 短信服务：发送短信
 └──→ 数据分析：记录行为
```

**消息队列的应用场景**

- 订单系统：在电商系统中，订单的创建、支付、发货等步骤可以通过消息队列进行异步处理和解耦；
- 日志处理：使用消息队列将日志从应用系统传输到日志处理系统，实现实时分析和监控；
- 任务调度：在批量任务处理、任务调度系统中，通过消息队列将任务分发给多个工作节点，进行并行处理；
- 数据同步：在数据同步系统中，消息队列可以用于将变更的数据异步同步到不同的存储系统或服务。

### MQ 解决的问题

1. 解耦

   生产者和消费者无需直接通信或相互依赖。生产者只需将消息发送到队列，不必关心消息由谁处理；消费者只负责从队列获取并处理消息，不必了解消息来源。这大大降低了系统间的耦合度，使得各个模块可以独立升级和扩容，避免了连锁故障。

2. 削峰填谷

   在秒杀、大促等高并发场景下，瞬时流量可能压垮后端服务。消息队列可以作为缓冲层，将突增的请求暂存起来，后端服务再根据自身处理能力匀速消费，从而保护系统不被过载。

3. 异步处理

   对于耗时较长或非实时性要求不高的任务（如发送注册邮件、生成报表等），生产者将消息投入队列后即可立即返回，无需等待消费者处理完毕。这极大地提升了主业务流程的响应速度和用户体验。

**引入 MQ 的代价**

虽然引入 MQ 有以上好处，但是多引入一个中间件，系统的稳定性就下降一层，运维的难度就抬高一层。具体来说有如下几个问题需要考虑：

1. 系统可用性降低

   MQ 挂了整个系统可能就挂了，所以要考虑 MQ 的高可用方案

2. 系统复杂度提高

   需要处理消息丢失、重复消费、消息顺序等问题

3. 一致性问题

   异步处理后如何保证数据最终一致性

因此，实际开发中要权衡利弊，系统是演进的，不要一上来就引入各种技术栈。

### MQ 的核心架构

最简化的消息队列架构就三个角色：生产者、Broker（Queue 和 Topic） 和消费者。

1. 生产者（Producer）

   负责构造消息，指定 Topic / Queue，发送消息，确认消息是否成功送达 Broker。例如：

   ```json
   {
     "messageId": "msg-001",
     "orderId": 10001,
     "userId": 123
   }
   ```

2. MQ 服务端（Broker）

   这是消息队列的“心脏”，负责消息的接收、存储、路由和转发。

   - 核心职责：接收发送方投递的消息，将其持久化落地（写入磁盘/数据库），然后根据路由规则将消息分发给对应的接收方。
   - 高可用与存储设计：
     - 分布式与多副本：通常采用分布式架构，支持集群扩展。例如，RocketMQ 采用 Master-Slave 主从多副本模式来保证高可用。
     - 高效存储模型：为支撑高并发，底层存储有专门的设计。例如，RocketMQ 采用 CommitLog（顺序写入所有消息）+ ConsumeQueue（逻辑消费队列）的模型，以实现极高的写入性能。
   - 可靠性保障：在消息投递的“下半场”，如果消息推送或拉取失败，服务端会采用“指数退避”等策略进行重发，以确保消息最终必达。

   消息的逻辑容器分为：

   - Queue 通常一条消息由某一个消费者处理。
   - Topic 同一类消息可以被多个业务订阅。

3. 消费者（Consumer）

   接收方是消息的最终处理者，由业务接收方和 MQ 客户端（MQ-client-receiver）组成。

   - 核心职责：从 MQ 服务端获取消息，执行业务逻辑，并向服务端发送确认（ACK）信号（如调用 `SendAck`）。服务端收到 ACK 后，才会将已落地的消息标记为完成或删除。
   - 消费模式：
     - 推模式（Push）：服务端主动将消息推送给消费者（如 RabbitMQ 的主流模式）。
     - 拉模式（Pull）：消费者主动向服务端轮询请求消息（如 Kafka 的主流模式）。

4. 辅助组件和路由机制

   除了上述三大核心模块，MQ 架构中还包含一些关键的辅助组件和路由机制：

   - 注册中心 / 路由管理：如 RocketMQ 的 NameServer，负责维护 Broker 的路由信息，使生产者和消费者能够动态发现并直连 Broker。
   - 路由分发中心：如 RabbitMQ 的 Exchange（交换机），它本身不存储消息，而是根据 Routing Key 和绑定规则，将消息精准路由到指定的队列中，实现生产者与队列的彻底解耦。
   - 多租户隔离：如 RabbitMQ 的 Virtual Host（虚拟主机），提供独立的命名空间，实现不同业务或环境间的资源与权限隔离。

### MQ 的模型

MQ 主要有两种模型：点对点模型（Point-to-Point）和发布/订阅模型（Publish/Subscribe）

**点对点模型**

这种模型也被称为队列模型，其核心特点是一对一通信。

- 工作机制：生产者将消息发送到特定的队列中，消费者从队列中获取消息进行处理。
- 消费特性：消息一旦被某一个消费者成功消费，就会从队列中被删除。即使有多个消费者监听同一个队列，每条消息也只会被唯一一个消费者处理。
- 适用场景：适用于任务处理类场景，例如一个耗时任务只需要一个处理者执行，或者多个消费者并行处理队列中的任务以实现负载均衡（如工作队列模型）。

**发布/订阅模型**

这种模型的核心特点是一对多通信（广播机制）。

- 工作机制：生产者将消息发布到一个特定的“主题（Topic）”或“交换机（Exchange）”上，而不是直接发送到某个队列。
- 消费特性：所有订阅了该主题的消费者（或订阅组）都会接收到相同的消息。每个订阅者都会独立处理这份消息，互不影响。
- 适用场景：适用于广播通知、实时推送、事件驱动架构等场景。例如，当电商系统产生一个新订单时，可以通过该模型同时触发库存扣减、积分计算和短信通知等多个异步处理流程。

### 如何处理重复消息、消息堆积、保证消息不丢失以及保证消息的有序性？

**如何处理重复消息**

MQ 中重复消息是不可避免的，只能靠消费端做幂等处理，保证同一条消息消费多少次结果都一样。

> 生产端产生重复
> 生产者发消息到 Broker，Broker 写入成功了但是响应超时，生产者以为失败了就重发一次，Broker 里就有两条一样的消息。想完全避免重复就得放弃 Broker 的响应确认，但这样消息可靠性就没了。
>
> 消费端产生重复
> 消费者拉到消息，业务逻辑跑完了，事务也提交了，正要更新 offset 告诉 Broker “我消费完了”，结果这时候消费者挂了。另一个消费者顶上来，发现 offset 没有更新，又把刚才那条消息消费了一遍。

两种主流方案：

1. 基于唯一标识去重

   给每条消息分配一个全局唯一 ID，可以用 UUID、雪花算法生成的 ID 或者业务单号。消费者收到消息后，先拿这个 ID 去 Redis 或数据库里查一下，查到了说明处理过了直接返回，没查到就执行业务逻辑然后把 ID 存进去。

2. 利用业务本身的幂等性

   比如利用数据库的主键或唯一索引机制。在处理消息插入或更新时，若发生主键冲突，则说明消息已被处理，直接跳过或返回成功。

   > 幂等性是指一个操作执行一次和执行一百次，最终结果都一样。

**如何处理消息堆积**

消息堆积是指在消息队列中，消息的生产速度远大于消费速度，导致大量消息积压在队列中。

解决思路分为“提高消费能力”和“优化处理流程”：

- 提高消费并发度：通过增加消费者节点数量，或在单节点内增加消费线程数来提升吞吐量。

  对于普通消息，并发度等于“单客户端线程数 × 客户端数量”。

- 优化业务处理逻辑：消息堆积往往是因为单条消息处理耗时过长（尤其是外部 I/O 操作，如数据库读写、RPC 调用）。应梳理下游依赖，优化代码逻辑，或将复杂的耗时操作进一步异步化。

- 限流和降级处理

  对生产端进行限流，比如使用令牌桶、漏桶算法等限流策略，降低生产速率，避免消息积压进一步恶化。

  对消费端进行降级，在消息堆积严重时，对低优先级的消息进行丢弃或延迟处理，只保留高优先级信息的消费，确保系统核心功能的正常运行。

- 完善监控预警：建立队列长度、消费延迟等指标的实时监控，在堆积达到阈值前及时告警并人工介入扩容。

**如何保证消息不丢失**

> 保证 MQ 消息不丢，需要从生产者、Broker 和消费者三个阶段保证：生产者使用发送确认和失败重试；Broker 做消息持久化和多副本；消费者采用手动 ACK，在业务执行成功后再确认消息。

保证消息不丢失需要需要生产、存储、消费三个环节共同配合，任何一个环节出问题消息都可能丢。

- 生产者端（发送确认）：开启发布确认机制（Publisher Confirm）。生产者发送消息后，必须等待 Broker 返回成功 ACK。若返回 NACK（失败） 或超时，则触发有限重试机制。
- Broker 端（持久化与高可用）：
  - 全链路持久化：确保 Exchange、Queue 和 Message 都开启持久化（落盘），防止 Broker 宕机导致内存中的消息丢失。
  - 集群与副本机制：采用多节点集群部署。例如 RocketMQ 的主从同步复制（SYNC_MASTER）或 Kafka 的多副本机制（acks=all），确保主节点故障时消息仍在从节点存活。
- 消费者端（手动确认）：关闭自动 ACK（autoAck）。消费者必须在核心业务逻辑完全执行成功后，再手动向 Broker 发送 ACK。若处理失败，可选择 NACK 并重新入队，或转入死信队列（DLQ）进行人工补偿。

**如何保证消息的有序性**

MQ 保证消息有序，核心是：让同一业务的数据进入同一个队列或分区，并且由消费者串行消费。

具体分三步：

1. 生产端保证同一业务 Key 的消息进入同一个队列/分区。
   例如同一个订单的“创建、支付、发货”消息，都根据 `orderId` 路由到同一个 Partition。
2. Broker 保证单个队列/分区内部消息有序。
   大多数 MQ 都只能保证“分区内有序”，不能天然保证全局有序。
3. 消费端保证串行处理。
   即使消息投递顺序正确，如果消费者开多线程并发处理，也可能出现后面的消息先执行完成，所以同一业务 Key 的消息要串行消费。

如果消费失败，还要保证前一条消息处理成功后再继续消费后续消息，否则也会破坏顺序。

### MQ 的推/拉模式

**推模式（PUSH）**

- 工作机制：由服务端（Broker）主导。当有新消息到达时，服务端会主动将消息推送给消费者。
- 优点：实时性极高，消息一旦到达，即可被立即投递和处理，延迟极低。
- 缺点：
  - 消息堆积与系统崩溃风险：服务端无法预知消费者的处理能力和当前状态。如果生产者的发送速率远大于消费者的处理速率，持续不断的推送会导致消费者缓冲区溢出、负载加重，甚至直接崩溃。
- 适用场景：对消息实时性要求极高，且消费者处理能力较强、资源充足的场景（如实时数据分析、交易系统通知）。

**拉模式（PULL）**

- 工作机制：由客户端（Consumer）主导。消费者主动向服务端发起请求，按需拉取一定数量的消息进行处理。
- 优点：
  - 流量与负载可控：消费者完全掌握消费节奏。可以根据自身当前的处理能力和系统负载，动态调整拉取的频率和每次拉取的数量，有效防止消息洪峰冲击。
  - 灵活处理历史数据：便于按需拉取、回溯或重放历史消息。
- 缺点：
  - 实时性与资源消耗的矛盾：如果拉取间隔设置过短，频繁的无效轮询（空轮询）会浪费网络 IO 和 CPU 资源；如果拉取间隔设置过长，又会导致消息消费不及时，增加延迟。
- 适用场景：需要严格控制消息处理速率、消费者处理能力有限，或者需要按需处理历史数据的场景（如日志采集、复杂业务逻辑处理）。

**长轮询（Long Rolling）：推拉结合的优化方案**

为了平衡拉模式的实时性与资源消耗，业界引入了长轮询机制（如 RocketMQ 的 Push 模式底层即是基于长轮询实现的）。

- **工作机制**：消费者发起拉取请求后，如果 Broker 端暂时没有新消息，不会立即返回空结果，而是将连接挂起（Wait）一段时间。在此期间，如果有新消息到达，Broker 会立即返回该消息；如果超过设定的超时时间仍无新消息，才返回空结果。
- **优势**：既保留了拉模式下消费者可控的优点，又大幅减少了无效的网络请求和 CPU 消耗，同时保证了极高的消息实时性。

## RocketMQ

阿里开源的金融级消息队列，原生支持分布式事务消息和精确到秒级的延迟消息，在保障数据最终一致性方面表现优异，广泛应用于电商和金融核心业务。



## Apache Kafka

一个分布式流处理平台，以其极高的吞吐量和水平扩展能力著称。它主要用于大数据领域的日志收集、流式数据处理和实时数据管道。









## RabbitMQ

一个轻量级且功能丰富的开源消息代理，完整支持 AMQP 协议。它提供复杂的路由逻辑、完善的 Web 管理界面，非常适合需要高可靠性和复杂业务路由的场景（如金融支付、物联网）。
